# 보안 (SECURITY)

사진 보안을 중심으로 한 Firebase 설계 문서. 규칙 파일은 레포 루트의 `firestore.rules`, `storage.rules`.

> **상태: 초안.** 규칙은 아직 테스트하지 않았다. 개발용 프로젝트에서 아래 "배포 전 확인"을 마치기 전에는 실제 사용자 데이터에 쓰지 않는다.

## 목표와 한계

- **막는 것**: 방 밖의 사람, 로그인하지 않은 사람, 링크만 아는 사람, 남의 폴더에 접근하려는 시도
- **막을 수 없는 것**: 같은 방 멤버가 결과 공개 후 사진을 캡처하거나 저장하는 것
- 따라서 "방 멤버가 아닌 사람은 절대 볼 수 없다"를 목표로 한다.

## 접근 규칙

| 대상 | 결과 공개 전 (`resultAt` 이전) | 결과 공개 후 |
|---|---|---|
| 내 제출 사진 | 나만 | 같은 방 멤버 |
| 다른 사람의 제출 사진 | 접근 불가 | 같은 방 멤버 |
| 내 미션(Assignment) | 나, 미션을 정해 준 사람 | 같은 방 멤버 (미션 공개 설정이 `public`이면 처음부터) |
| 투표(Vote) | 불가 | 같은 방 멤버 (본인 투표는 본인만 읽기) |
| 시상(Award) | 불가 | 같은 방 멤버 |

- `resultAt`이 비어 있으면 결과 공개 전으로 본다.
- 사진 업로드와 교체는 `deadlineAt` 전까지만 가능하다. (Firestore 제출 문서 기준)
- 비로그인 사용자는 모든 경로에서 거부한다.

## 인증

- Firebase **Anonymous Auth**(익명 로그인)를 기본으로 쓰고, `uid`를 `User.id`로 사용한다.
- `Player` 문서의 ID는 `userId`와 같게 둔다. (`rooms/{roomId}/members/{uid}`)
- 규칙은 이 `members/{uid}` 문서가 있는지로 방 멤버를 판단한다.

## 사진 처리

1. **업로드 전에 줄인다.** 긴 변 1024px JPEG로 다시 그리면 촬영 위치(GPS) 등 EXIF가 제거된다. (`apps/web/src/lib/image.ts`) 업로드할 때는 원본이 아니라 이 결과물을 올린다.
2. **경로**: `rooms/{roomId}/submissions/{uid}/{submissionId}.jpg`
3. **제한**: 본인 폴더에만, JPEG, 5MB 미만. 같은 경로에 올리면 교체된다.
4. **Firestore에는 경로만 저장한다** (`Submission.photoPath`). `getDownloadURL()`이 주는 URL은 토큰이 포함되어 있어 링크를 아는 사람은 규칙과 무관하게 열 수 있으므로 저장하거나 공유하지 않는다.
5. **읽을 때**는 로그인한 상태에서 SDK로 내려받는다. (`getBlob()` 또는 `getBytes()`, 정확한 API는 Firebase 문서 확인) 받은 데이터를 `URL.createObjectURL`로 화면에 보여준다.
6. **삭제**는 클라이언트에 허용하지 않는다. 보관 기간이 지난 사진은 서버가 정리한다.

## 서버(Cloud Functions)가 맡을 일

클라이언트에 맡기면 조작될 수 있는 일은 서버에서 처리한다.

| 일 | 이유 |
|---|---|
| 방 참가 (초대 코드 확인 후 `members` 문서 생성) | 규칙만으로는 초대 코드를 안전하게 검증할 수 없다 |
| 방 상태 전이 (`playing` → `finished`, `resultAt` 도달) | 방장 클라이언트의 시계·조작에 의존하지 않기 위해 |
| 시상 계산과 `Award` 기록 | 수상 결과 조작 방지 |
| 보관 기간이 지난 사진 삭제 | 유출될 대상 자체를 줄이기 위해 |

초대 코드는 추측하기 어려운 길이로 만들고, 만료와 시도 횟수 제한을 둔다.

## 그 밖의 방어

- **App Check**: 우리 앱이 아닌 곳에서 오는 요청을 막는 추가 방어층. Firestore와 Storage에 적용한다.
- **공유**: 인스타그램에는 사용자가 직접 내보내는 **결과 카드 이미지**만 공유한다. 원본 사진은 공개하지 않는다.
- **Firebase 웹 설정값**(apiKey 등)은 원래 공개되는 값이다. 보안은 규칙이 담당한다.
- **클라이언트**: HTTPS만 사용, `dangerouslySetInnerHTML` 사용 금지, 사용자 입력(닉네임 등)은 그대로 HTML로 넣지 않는다.

## 배포 전 확인

에뮬레이터는 쓰지 않으므로 **개발 전용 Firebase 프로젝트**에 규칙을 올려서 확인한다. 실제 사용자 사진이 들어오는 프로젝트에는 아래를 모두 통과한 뒤에 배포한다.

1. 개발용 프로젝트와 운영용 프로젝트를 분리한다.
2. 규칙을 배포한다. (`FIREBASE_SETUP.md` 4번)
3. 아래 표를 확인한다. 방법은 두 가지다.
   - **앱**: 일반 창과 시크릿 창으로 접속하면 서로 다른 익명 계정이 된다.
   - **콘솔의 규칙 플레이그라운드**: 로그인 여부와 uid를 바꿔 가며 읽기/쓰기를 시뮬레이션한다. 방 멤버 문서(`rooms/{방ID}/members/{uid}`)나 `resultAt`, `deadlineAt` 값은 콘솔의 데이터 화면에서 직접 만들거나 고쳐서 상황을 만든다.
4. 확인이 끝나면 만든 가짜 멤버 문서와 바꾼 값을 되돌린다.

| # | 상황 | 기대 결과 | 확인 방법 |
|---|---|---|---|
| 1 | 비로그인 사용자가 사진·문서를 읽기/쓰기 | 거부 | 플레이그라운드(미인증) |
| 2 | 로그인했지만 방 멤버가 아닌 사용자가 사진·문서 읽기 | 거부 | 시크릿 창에서 방 주소(`/room/{방ID}/play`)로 접속 |
| 3 | 멤버, 결과 공개 전, 내 사진 읽기 | 허용 | 앱: 제출 후 새로고침해도 사진이 보임 |
| 4 | 멤버, 결과 공개 전, 남의 사진 읽기 | 거부 | 콘솔에서 가짜 멤버(uid 예: `test2`) 문서를 만들고 그 uid로 플레이그라운드 |
| 5 | 멤버, 결과 공개 후, 남의 사진 읽기 | 허용 | 콘솔에서 `resultAt`을 과거 시각으로 바꾼 뒤 플레이그라운드 |
| 6 | `resultAt`이 비어 있을 때 남의 사진 읽기 | 거부 | `resultAt`이 `null`인 상태에서 4번과 같게 확인 |
| 7 | 남의 uid 폴더에 업로드 | 거부 | 플레이그라운드(Storage) |
| 8 | PNG 또는 5MB 이상 파일 업로드 | 거부 | 플레이그라운드(Storage), 지원하는 범위에서 확인 |
| 9 | 마감(`deadlineAt`) 후 제출 문서 생성·수정 | 거부 | 콘솔에서 `deadlineAt`을 과거로 바꾼 뒤 앱에서 제출 |
| 10 | 남에게 배정된 Assignment로 제출 문서 생성 | 거부 | 플레이그라운드(Firestore) |
| 11 | `photoPath`가 내 uid 경로와 다른 제출 문서 생성 | 거부 | 플레이그라운드(Firestore) |
| 12 | 클라이언트에서 `Award` 쓰기, 사진 삭제 | 거부 | 플레이그라운드 |

Storage 규칙은 Firestore를 조회하므로, 처음 배포할 때 서비스 간 권한 허용 안내가 뜬다. 한 요청에서 조회할 수 있는 횟수 제한과 과금 영향도 Firebase 문서에서 확인한다. (읽기 규칙은 조회를 2번 한다)

## 현재 코드의 상태

- 지금은 사진이 사용자 브라우저의 localStorage에만 저장되고 서버로 가지 않는다. (`apps/web/src/lib/mockDb.ts`)
- mockDb는 Firebase와 같은 구조(경로만 `Submission`에 저장, 사진 데이터는 별도 보관)로 되어 있어서, Firebase 연결 시 이 파일만 교체하면 된다.
- mockDb에는 보안이 없다. 개발용이다.

## 열린 질문

1. **투표 시점**: 투표하려면 다른 사람의 사진을 봐야 하는데, 사진은 결과 공개 이후에만 볼 수 있다. 현재 규칙은 투표를 결과 공개 이후로 두었다. 시상식 흐름과 맞는지 확인이 필요하다.
2. **보관 기간**: 게임 종료 후 며칠 뒤에 사진을 삭제할지.
3. **익명 로그인 한계**: 익명 계정은 앱 데이터를 지우거나 기기를 바꾸면 되찾을 수 없다. 로그인(소셜 등)을 붙일지.
4. **시간 타입**: 모델은 시간을 ISO 문자열로 두었지만 Firestore 규칙은 Timestamp 타입을 쓴다. 연결 시 변환 계층이 필요하다.
5. **Firestore 문서 크기·쿼리 제약**: 규칙은 필터가 아니므로, 목록 조회 쿼리는 규칙 조건과 맞게 작성해야 한다.
